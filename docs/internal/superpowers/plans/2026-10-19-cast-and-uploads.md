# Cast, voices, faces and full novel uploads — plan

Spec: this file (user request 2026-10-19, rulings below). Subagents: Sonnet 5.5 medium only. No Claude attribution in commits.

## What the user asked for
- Uploaded **novels** get the Harry Potter treatment: character voices for **main characters only**, dialogue split by speaker, summaries (so recap and spoiler-safe talk work), search index.
- Uploaded **textbooks**: no characters; just narrator voice + face selection in both modes.
- **Reading mode**: a toggle between **one voice reads everything** and **full cast**. One-voice mode: pick the voice and face. Full cast: pick a voice and a face for the narrator and each main character. No spoiler gating on this cast list.
- **Talk mode**: one character answers at a time (character dropdown). Voice dropdown: **Auto** (that character's reading-cast voice) or a specific voice. Avatar dropdown: **Auto** or a specific face. The spoiler toggle affects only answer content (already built).
- Voices: upload mp3/wav or record → clone → saved and selectable (exists). Faces: upload any image → saved and selectable, not only together with a voice clone.

## Rulings
- R1 Main characters = at most 8 per uploaded novel, chosen by Claude's cast pass by importance (speaking lines + plot role). Minor speakers are read by the narrator voice in full-cast mode. Cost if wrong: re-run cast with a different cap.
- R2 Cast/face/voice assignments are stored **server-side per book** (`data/books/<id>/cast_settings.json`, gated by the access code) so they persist across devices; the browser keeps only the reading-style and talk dropdown choices in localStorage. Single-user hackathon app, so one shared setting per book is fine. Cost if wrong: move to localStorage.
- R3 The Claude key goes to Secret Manager as `anthropic-api-key`, mounted only on the `talkback` service. Uploaded-novel processing shows a cost estimate and needs an explicit "Process with characters (~$X)" confirmation; a server-side cap refuses jobs estimated above $4 and keeps a running spend total in `data/usage` with a hard stop at $15 cumulative upload spend. Cost if wrong: a few dollars.
- R3a (user, 2026-10-19) The estimate/confirm step is visible only in testing mode (`UPLOAD_CONFIRM=true` env, default false). In demo mode processing starts straight after upload with no cost UI; the $4-per-book and $15-cumulative caps still apply silently server-side (a refused job shows a plain "This book is too long to process with characters; it will be read by the narrator" message).
- R4b Speed target: a novel processed in ~3–5 minutes, not 10–20. The book is readable (narrator only) seconds after upload; voices, recap and character talk switch on as stages finish. Segmentation runs at high concurrency (≥ 24, batched 10 paragraphs per call). Summaries are no longer a sequential chain: chapter notes are written in parallel (one per chapter plus in-chapter checkpoints every ~40 paragraphs, each from that chapter's text up to the checkpoint), and the story-so-far at a position = condensed notes of completed chapters + the current chapter's latest checkpoint. Every note still uses only text at or before its `upto_para` (spoiler invariant). Embeddings are batched.
- R4c (user, 2026-10-19) The upload pipeline's LLM is pluggable: a developer-only env setting `UPLOAD_LLM=claude|gemini`, default **claude** (no UI for it). `gemini` = Gemini 2.5 Flash on Vertex, paid from GCP credit. With `claude`, an `insufficient_quota` / billing error switches the rest of the job to Gemini automatically, so running out of Claude credit never breaks uploads. Same prompts, same verbatim check and narrator fallback for segmentation, same cost caps (priced per provider). The offline `preprocess/` scripts get the same switch (`LLM_PROVIDER`) so they can run on Gemini too.
- R4 Uploaded novels use Haiku 5.5 for segmentation and **summaries** (HP used Sonnet for summaries) to keep a novel around $1–2. Cast stays Sonnet (one call). Cost if wrong: summaries slightly worse.
- R5 Face loops (talk/idle animation) are generated only when the user clicks "Animate this face" (a few cents of Boson avatar credit), with the cost shown on the button. Without loops a face shows as a still portrait (plus the existing optional lip-sync).
- R6 Processing runs as a background task in the Cloud Run instance; the frontend polls status every few seconds, which keeps the instance alive (no CPU throttling is already set). Cost if wrong: a long novel's job dies when the instance scales down; the status then says "interrupted, upload again".
- R7 Reading-mode cast panel shows all main characters (no spoiler gating), per user. Talk-mode character list stays gated by reader position unless spoilers are on (already built).

## Tasks (run one at a time, in order)
1. **Face library + cast settings API (backend).** Standalone face upload/list/delete (`/api/faces`), "animate face" endpoint generating talk/idle loops via the existing Boson avatar path (`scripts/make_face_loops.py` logic moved into the app), `GET/PUT /api/books/{id}/cast` storing narrator + per-main-character `{voice, face}` and the book's main-character list. Tests.
2. **Reading/Talk selection UI (frontend).** Reading style toggle (One voice / Full cast) with pickers; full-cast table for narrator + main characters (voice dropdown: presets + cloned voices; face dropdown: faces library + "none"); upload-face and clone-voice entry points; Talk panel Voice (Auto/choose) and Avatar (Auto/choose) dropdowns; textbooks show narrator only. Replaces the current localStorage series overrides (migrate them once). Tests.
3. **Novel upload pipeline (backend).** After text ingest of a novel: estimate → wait for confirmation → cast (main ≤ 8) → segment (Haiku) → summaries (Haiku) → chunk_tts → local index, and Vertex index when RETRIEVAL_BACKEND=vertex. Progress status with stage names and percentages, cost cap, spend tracking. Reuse `preprocess/` modules (import them from the backend, or move shared pieces into `backend/app`). Upload UI shows the estimate and a confirm button. Tests with Claude mocked.
3b. **Auto-detect book kind + library shelves (user, 2026-10-19).** Upload form's kind selector defaults to **Auto-detect** (still overridable: Novel / Textbook). Detection: one cheap LLM call (same UPLOAD_LLM provider, Gemini fallback) on ~3,000 chars sampled from the start, middle and end, returning novel|textbook + confidence; heuristic fallback if the call fails (dialogue-quote ratio, "Figure/Table/Exercise/Chapter summary" markers, numbered section headings). The library home page shows two shelves, **Novels** and **Textbooks**, series grouped inside Novels (Harry Potter 1–7 in order). Each uploaded book's card has "Move to Textbooks / Novels"; moving a textbook to Novels starts enrichment (same caps), moving a novel to Textbooks just changes the kind (characters ignored). Tests.
4. **Deploy.** Create the `anthropic-api-key` secret, add it to `scripts/deploy_cloudrun.sh`, redeploy, smoke-test the live site (books list, recap, spoiler toggle, a short text upload).
5. **Final review** (Sonnet), fixes, push.

The answer-quality work (bigger chunks, k=8, prompts, re-index) and its after-eval run separately and land before task 3.
